# Yaesu FTM-200D data port (phase 9)

What the FTM-200D sends out of its data port, and what the FTM-200 backend
(`aprsx/core/ftm200.py`) handles. The format was first taken from the user's old
`ftm200_aprs_bridge.py`. It was **confirmed by a capture on 2026-09-25**
(`tests/data/ftm200/capture-20260925.raw`, see *Findings*). Anything still marked
*unconfirmed* hasn't come up in a capture yet.

## Hardware

```
FTM-200D DATA jack ── Yaesu SCU-66 (USB serial) ── Pi USB ── /dev/serial/by-id/usb-…
```

- The SCU-66 is a **Prolific PL2303** (USB `067b:23a3`, kernel driver `pl2303`) and
  shows up as `/dev/ttyUSB0`, by-id
  `/dev/serial/by-id/usb-Prolific_Technology_Inc._USB-Serial_Controller_<serial>-if00-port0`.
  `deploy/install.sh --radio ftm200` looks for `*Prolific*` there. With the Heltec
  plugged in there are two non-CP210x ports, so the capture tool needs `--device`.
- The cable in use is the SCU-66 (the older scripts' "SCU-56" was a typo).
- gpsd leaves the port alone (`USBAUTO="false"` in `deploy/gpsd.default`). The Pi has
  no ModemManager or brltty that might probe it, and `pi` is in `dialout`.
- The bridge holds RTS and DTR low. The capture tool does the same, until we know
  whether the radio or cable pays attention to them.

## Radio settings

Menu numbers are from the FTM-200DR/DE Advance Manual (hold **[F MENU]**, turn the
dial to the item, press the dial; **[SQL BACK]** goes back).

| Setting | Value | Why |
|---|---|---|
| APRS modem | On | The radio only decodes APRS with it on |
| 66 COM PORT → OUTPUT | **PACKET** (factory default OFF) | Other choices are GPS OUT (NMEA) and WAYPOINT. With OFF the port is silent |
| 66 COM PORT → SPEED | 9600 (factory default) | Must match `ftm200.baud` |
| 67 DATA BAND → APRS | The band tuned to 144.390 | The band the APRS modem decodes |
| 68 DATA SPEED → APRS | 1200 bps | Standard APRS |
| 71 APRS FILTER | Mic-E, POSITION, WEATHER, OBJECT, ITEM, STATUS, OTHER on; RANGE LIMIT off | Assumed to limit what gets output as well as what's shown. *Unconfirmed* |

WP FORMAT and WP FILTER under 66 only apply to WAYPOINT output.

## Line format (confirmed)

Each packet arrives as two lines:

```
KC0BS-10>3XUW9Q,TNGNXI,WIDE1,STJOHN,W0NH-1,WIDE2* [09/25/26 12:32:27] <UI R>:
`zJ^l"Ik\`"7D}kc0bs.com_%
```

1. **Header:** `SRC>DEST,PATH`, then a space, a bracketed timestamp, an optional
   `<…>` frame-type tag, and a trailing `:`. The bridge matches it with
   `^([^ >\r\n]+>[^\s\[]+)\s+\[[^\]]+\](?:\s+<[^>]*>)?\s*:\s*$`.
2. **Info field** on the next line, unchanged.

The backend (`ftm200.LineParser`) builds TNC2 as `header + ":" + info`, decoding
bytes as Latin-1 so Mic-E bytes survive, and ignores blank lines and anything that
doesn't follow a header.

## Questions the capture has to answer

Answered from `capture-20260925.raw` (see *Findings*) unless marked open.

- [x] Serial settings: 9600 baud 8N1, lines end `\r\n`, nothing between packets
- [x] Header: `[MM/DD/YY HH:MM:SS]` from the radio's own clock (an hour behind on the
      test radio, so not GPS or local time); tags `<UI>` (31), `<UI R>` (14),
      `<UI C>` (9): the AX.25 command/response bits, not used
- [x] Path: TNC2 convention, `*` on the last used hop only
      (`...,W0NH-1,WIDE2*`, `STJOHN>APU25N,W0NH-1,WIDE1*,WIDE2-2`)
- [ ] Info field: complete and unchanged as far as can be seen (Mic-E control bytes
      and backslashes intact, trailing spaces kept). **Open:** a side-by-side check
      against Direwolf, which needs the Digirig and FTM-200 on the air together
- [x] Packet types seen: uncompressed positions (30), Mic-E (11), objects (9),
      compressed (3). Messages come through too, to the FTM-200's own call and to
      others (on-air test 2026-09-25, below). **Open:** status, telemetry, weather-only,
      third-party
- [x] Duplicates: digipeated copies are all output. STLSMI came twice 11 s apart
      by different paths (`W0NH-1,WIDE1*,WIDE2-2` then a 5-hop path)
- [x] The FTM-200's own transmissions aren't echoed directly: its ack to a message
      (`KF0KBP-9`) showed up only as W0NH-1's digipeated copy
      (`KF0KBP-9>APY200,W0NH-1,WIDE1*,WIDE2-1::KF0KBP-1 :ack013`)
- [x] Nothing else appears: no NMEA, banner or status lines in 50 minutes
- [x] Does the radio react to input? Not tried. The manual lists the port as output
      only, so the backend never writes to it

## Capture procedure

The capture tool is `tools/ftm200_capture.py`. It's read-only and runs on the
Pi's system python3.

1. Plug the SCU-66 into the Pi and set up the radio as above.
   `ls -l /dev/serial/by-id/` should now show a second entry.
2. Find the speed if it's not known: `python3 ~/aprsx/tools/ftm200_capture.py --scan`
   (60 s at each speed; the right one gives printable text and packet headers).
3. Record: `python3 ~/aprsx/tools/ftm200_capture.py --baud 9600 --seconds 3600`.
   This writes `~/ftm200-capture-<time>.raw` (exact bytes) and `.log` (timestamped
   lines).
4. **Reference copy:** leave `aprsx-core` running on the Digirig and UV-5R during the
   capture. The same over-the-air packets are then logged by Direwolf in the core's
   `packets` table, so each FTM-200 line can be compared with Direwolf's TNC2
   for the same packet (match on source and info within a few seconds).
5. For packet types that don't come up by themselves (messages, objects, Mic-E),
   send known packets from KF0KBP-7 on the Digirig, **only with the user's OK**, since
   that transmits. Also note which of the FTM-200's own beacons and messages were
   sent during the capture.
6. Copy the files into `tests/data/ftm200/` for WP9.6. Before committing, cut them down
   to a representative set.

## Findings

**2026-09-25, `capture-20260925.raw`** (13:30–14:20 CDT, 54 headers, 53 whole packets,
FTM-200D at the test Pi's location, SCU-66 at 9600):

- The format matches the old bridge. The backend drops the timestamp and tag and uses
  the Pi's arrival time.
- 26 of the packets are followed by an empty line (`\r\n\r\n`). They're mostly
  digipeater and iGate beacons, probably info fields ending in CR. The parser skips
  blank lines.
- **One info line was cut off:** KB1EMU-6's Mic-E came out as `4P` with no line end,
  and the next header followed 36 s later on the same line. Read as-is, that would be
  a station called `4PKF0WGF-9`. The reader drops a partial line (and its packet) after
  1 s without bytes (`ftm200.IDLE_FLUSH_S`), since the radio writes each line at once.
- Receive stops while the radio's receiver is busy (voice traffic on the band); the
  port simply goes quiet.
- **Only one program can read the port.** A leftover capture kept the port open for
  25 minutes after the core opened it too; the capture got every byte and the core
  none. The core now takes pyserial's `flock` as well as `TIOCEXCL`, so it reports
  "in use by another program" and retries instead.
- **Messages (on-air test, 14:33–14:37):** from the base station KF0KBP-1, a message to
  the FTM-200's call (KF0KBP-9) was shown and acked by the radio. One to the Pi's call
  (KF0KBP-7) reached the core and showed on the head unit:
  `KF0KBP-1>APGRWO,WIDE1-1,WIDE2-1::KF0KBP-7 :testing{014`. The core couldn't ack it
  (receive-only, APRS-IS unverified), so the base retried it 4 times, 30 s apart.
  With the APRS-IS passcode set (14:42), a reply from the Pi went out over APRS-IS
  and was acked, and the next message from the base (over RF) was acked over APRS-IS
  at once, with no retries. KF0KBP-1 is itself on APRS-IS, so no iGate was needed.
  For RF-only stations, delivery depends on an IS→RF iGate near them.
- The Pi logged "Undervoltage detected" when the cable was plugged in; worth a better
  supply in the car.
